# 午餐小鎮完整版規劃書

撰寫日期：2026-11-06　基底版本：`main`（DevDays 展示版）
每一項工作都有對應的 GitHub issue，以里程碑標籤 `M1`～`M4` 與決策標籤 `decision` 分類。

## 1 現況：展示版已經有什麼

DevDays 展示版是一條完整、可以多人實際操作的縱切，細節見 `PLAN.md`：

| 範圍 | 已完成 |
| --- | --- |
| 團購 | 開團（凍結菜單）、分享網址加入、＋1／−1、即時彙總、收單、匯出文字 |
| 正確性 | `BEGIN IMMEDIATE` 交易、requestId 去重、收單與點餐競態、revision 對齊、斷線重送 |
| 遊戲 | RPG Maker 風格點陣街區（960×608 可捲動）、走進店內、陳列台＋Enter 點餐、同場角色、點餐泡泡 |
| 店家 | 開店精靈、菜單編輯、營業切換、管理碼認領、收單後即時收到訂單、接單／拒單／製作中／可取餐 |
| 外送 | 店家分段距離門檻、開團選送餐地點、未達標可改自取 |
| 收款 | 團主設定收款方式並傳送、團員回報付款、團主確認（不經手金流） |
| 資料 | 台中 6 家真實店家種子資料、增欄遷移 |
| 測試 | 90 項 Vitest、雙瀏覽器煙霧測試腳本 |

**展示版刻意省略、完整版必須補上的部分：**

1. **身分**：全部是匿名 Cookie；店家靠一次性管理碼，另有共用展示碼 `demo` 可接管所有種子店家。
2. **上線條件**：只在本機或 ngrok 執行；沒有 CI、備份、監控、速率限制，也沒有資料清理。
3. **點餐細節**：不能加備註或選項（加飯、辣度），沒有截止時間，團主無法管理成員。
4. **店家營運**：沒有營業時間、售完、限量、自訂圖片，新單只有頁面內提示。
5. **手機**：沒有觸控移動，只能用「前往店家」按鈕。
6. **規模**：地圖固定 12 個店面格；外送距離以像素換算，不是真實距離。

## 2 目標與非目標

**目標：** 讓一個辦公室（或一棟大樓）每天真的用午餐小鎮揪團訂便當，店家也願意每天打開後台接單。

成功指標（上線三個月內觀察）：

- 每週至少 3 次真實揪團，每團平均 5 人以上。
- 從開團到收單的中位時間 15 分鐘以內。
- 店家回覆率：送出的訂單 90% 在 10 分鐘內被接單或拒單。
- 正確性：零重複加單、零金額錯誤回報。

**非目標（完整版仍然不做）：**

- 線上金流、代收代付、自動對帳。收款仍然只傳遞資訊。
- 外送媒合與外送員調度。
- 多城市平台化、廣告與抽成機制。
- 原生 App。以手機瀏覽器與 PWA 為主。

## 3 里程碑

| 里程碑 | 主題 | 完成判定 |
| --- | --- | --- |
| **M1 可上線** | 部署、備份、CI、安全強化、資料清理、監控 | 有固定網址的正式環境可以連續一週不靠人照顧；展示碼在正式環境無效 |
| **M2 點餐完整** | 選項與備註、截止時間、團主管理、歷史與再揪一次、手機觸控、通知 | 一般同事不看說明就能用手機完成一次完整揪團 |
| **M3 店家營運** | 店家帳號、營業時間、售完與限量、菜單匯入、自訂圖片、新單通知、報表 | 一家真實店家連續一週用後台接單 |
| **M4 小鎮擴展** | 多街區、真實距離、社交互動、成就與道具、NPC 與小動物、飲食標籤、無障礙 | 店家數超過 12 家時地圖仍好逛；距離與實際相差 20% 以內 |

順序原則：**M1 是其他里程碑的前提**，一定要先完成。M2 與 M3 可以並行。M4 依使用量決定是否做。

## 4 各里程碑內容

### M1 可上線

- **部署與持久化**：選定常駐主機（見決策 D2），以 Docker 映像部署，SQLite 放在持久化磁碟。工作目錄已有一份 Railway 用的 `Dockerfile` 草稿，但它用 Node 24，專案是在 Node 26 開發的（依賴 `node:sqlite`），需要統一版本。單一實例即可，不需要水平擴展。
- **備份**：SQLite 線上備份（Litestream 或每小時 `VACUUM INTO`）到物件儲存，並做一次還原演練。
- **CI**：GitHub Actions 跑 `typecheck`、`test`、`build`，以及 headless Chrome 的煙霧測試。
- **安全強化**：
  - 正式環境停用 `DEMO_KEY`，種子店家改由正式帳號認領。
  - API 與 Socket 的速率限制、請求大小上限。
  - CSRF 防護：已有 `SameSite=Lax`，再要求自訂標頭。
  - 安全標頭（CSP、HSTS），`COOKIE_SECURE=1`。
- **資料保留**：
  - 已收單超過 30 天的團封存或刪除，收款帳號資料要一起清除。
  - 清理過期 session 與 `processed_requests`。
- **監控**：結構化 log、`/healthz`、外部 uptime 檢查、錯誤通知。

### M2 點餐完整

- **餐點選項與備註**：
  - 店家可以定義選項群組（例如「飯量：正常／加飯 +10」「辣度」）。
  - 團員點餐時可以選選項並加文字備註，彙總與匯出依選項分列。
  - 這會改動點餐交易的鍵（`meal_id` 變成 `meal_id + 選項組合`），需要遷移與完整測試。
- **截止時間與自動收單**：開團時可設截止時間，倒數顯示；時間到由伺服器自動收單，與手動收單走同一個交易。
- **團主管理**：移除成員（並刪除其訂單）、代他人點餐、收單後重新開團（複製成員與訂單）。
- **歷史與再揪一次**：「我的團」列表，可以用同樣的店家與送餐地點一鍵再開一團。
- **手機觸控**：虛擬搖桿或點地移動，手機版面重新排版，進店與點餐都能單手完成。
- **通知**：用 Web Push（PWA）通知團員：店家接單、可取餐、收款資訊到了、團主確認收款。
- **收款補強**：收款帳號可產生 QR code（只產生、不處理付款），團主可對未付款的人發提醒。

### M3 店家營運

- **店家帳號**：取代一次性管理碼，方案見決策 D1。一家店可以有多位管理者。
- **營業時間**：每週營業時段；非營業時段不出現在新團，也可設每日接單截止時間。
- **售完與限量**：店家可以即時標記售完。限量餐點在點餐交易內檢查剩餘數量。
  - 這會影響凍結菜單：進行中的團要能看到售完狀態，但價格仍然凍結。
- **菜單匯入**：貼上文字或菜單照片，AI 轉成菜單草稿，店家逐項確認後上架。AI 只做草稿，不參與點餐與計價。
- **自訂餐點圖片**：上傳照片自動轉成點陣風格，或在 32×32 像素畫板上自己畫。
- **新單通知與出單**：Web Push、LINE 通知（依決策 D1 的帳號綁定），可以列印出單（熱感紙版面）。
- **營運報表**：日、週訂單數與營業額，熱門品項，拒單原因統計。

### M4 小鎮擴展

- **多街區地圖**：店面格不再固定 12 格。地圖依區域分成多個街區，街區之間可以傳送；店家依真實位置自動分配地段。
- **真實距離**：店家與送餐地點用經緯度儲存，距離用真實座標計算（直線或路徑 API），像素地圖只負責呈現。
- **社交互動**：表情、揮手、同店顯示「誰也在這家店」，可以在設定裡關閉。
- **飲食標籤與預算**：素食、辣、含蛋奶等標籤；團員可設預算，超過時提醒。
- **無障礙**：不經過遊戲畫面的純表單點餐路徑；鍵盤與螢幕閱讀器可以完成全流程。
- **成就**：
  - 團員：第一次揪團、逛遍所有店、連續 5 個工作日點餐、全團準時付清。
  - 店家：第一次接單、連續 10 單零拒單。
  - 成就由伺服器在交易提交後依事件判定，不能由前端宣告。
  - 成就名稱不透露點了什麼。別人只看得到徽章，而且可以隱藏。
- **道具撿拾**：
  - 街區路邊會隨機出現小道具，例如花、貓、落葉、硬幣造型的貼紙。角色走過去就會撿起來，放進背包。
  - 每個人看到的道具各自獨立，不用搶。生成清單由伺服器決定；撿拾時伺服器會比對該角色在記憶體中的位置，避免直接呼叫 API 灌道具。
  - 道具只有收藏與裝扮用途，**不能折抵金額，也不影響點餐**。收集到一整組可以解鎖角色配件（帽子、背包）。
- **NPC 與小動物**：
  - 街區有村民 NPC，還有貓、狗、鴿子、雞，會在人行道和空地上隨意走動。
  - 只在前端模擬，不經過伺服器。用「團 ID＋時間」當亂數種子，同一團的人看到的位置大致相同，也不會增加網路流量。
  - 靠近時可以互動：村民說一句話（小鎮小知識、哪家店營業中），摸摸小動物時會冒出愛心。互動可以計入 #33 的成就，例如摸過 10 隻貓。
  - 不擋門口和路，也不會走進店內。在手機上可以減少數量或關閉。
- **身分**：成就與背包綁定身分。沒有帳號時跟著 Cookie session 存 30 天，有帳號後才能跨裝置保存（依 D1）。

## 5 架構方向

展示版的架構可以沿用到完整版，以下是需要調整的地方：

| 項目 | 展示版 | 完整版 |
| --- | --- | --- |
| 執行環境 | 本機 Node 26 + tsx | Docker 映像，固定 Node 版本；正式環境先編譯，不用 tsx 直接執行 |
| 資料庫 | 單檔 SQLite、啟動時增欄遷移 | 仍用 SQLite＋線上備份；遷移改成有版本號的遷移檔 |
| 身分 | 匿名 Cookie＋管理碼 | 團員維持匿名（低門檻）；店家與常用團主可登入綁定帳號 |
| 即時 | 單實例 Socket.IO | 單實例足夠；若要多實例，改用 Redis adapter，presence 也移到 Redis |
| 前端 | Vite + React + Canvas | 加上 PWA（Service Worker、Web Push）；觸控輸入層 |
| 契約 | `shared/contracts.ts` 宣告合併 | 定為 v1 API 並加上版本前綴，選項等破壞性改動走 v2 |

## 6 待決事項

這些需要先做決定才能開工，每一項都有一張 `decision` issue：

| 編號 | 問題 | 建議 |
| --- | --- | --- |
| D1 | 帳號方案：LINE Login、Email 魔法連結，還是公司 SSO | 先做 LINE Login：店家與同事都有 LINE，也能順便發通知 |
| D2 | 主機與預算：Fly.io、Railway、自有 VPS，還是公司內部主機 | 選一個有持久化磁碟、月費 10 美元以內的方案 |
| D3 | 產品定位：公司內部工具，還是公開讓任何團與店家使用 | 先做公司內部，店家由我們邀請上架，可以延後審核機制 |
| D4 | 店家上架審核：誰能開店、如何驗證是真的店家 | 依 D3 決定；內部工具階段由管理員邀請 |

## 7 風險

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| 店家不習慣開後台 | 訂單送不到店家 | 保留「匯出文字」讓團主自己打電話；新單用 LINE 推播 |
| 選項改動點餐交易的鍵 | 去重、彙總、匯出都可能出錯 | 獨立遷移、完整重跑規格第 11 節 fixture 與並發測試 |
| SQLite 單機故障 | 資料遺失 | 持續備份＋還原演練；保留匯出文字當人工備援 |
| 收款帳號屬於個資 | 外洩疑慮 | 只對團內成員顯示、過期清除、log 不記錄收款資料 |
| 遊戲化讓人分心或比較壓力 | 點餐變慢、有人不想參加 | 道具只出現在街區，不出現在店內與點餐面板；成就與徽章都可以關閉 |
| 手機上遊戲操作比較慢 | 使用者放棄 | 一律保留「前往店家」按鈕與純表單點餐路徑 |
