# Sites 團單與角色同步

追蹤：#39。依 #2 的驗證結論，Sites 上只確認了 HTTPS API 與單一連線的 WebSocket echo；跨 Worker 廣播、Durable Objects、Queues、Cron 都未驗證。因此 Sites 版採用 HTTP 輪詢加上持久化的 revision。Node 開發伺服器仍使用 Socket.IO（`server/realtime/realtime.ts`）。

## 資料分層

| 資料 | 存放位置 | 一致性 |
| --- | --- | --- |
| 團、成員、訂單、收單、付款 | D1 `app_state`：整個 SQLite 快照為一個 blob | 寫入時以 `revision` 做樂觀鎖，衝突最多重試 8 次；訂單用 `requestId` 去重 |
| 角色位置 | D1 `live_presence`，以團、成員、連線為主鍵 | 可丟棄；10 秒沒更新視為離線 |
| 點餐泡泡 | 快照內的 `live_bubbles`，與該筆點餐在同一次寫入 | 保留 30 秒，以 cursor 增量讀取 |

角色移動只寫 `live_presence`，不會寫入訂單快照。

## 同步頻道

前端（`web/adapters/sites-live.ts`）輪詢 `POST /api/rooms/:id/live`：

- **請求：** 帶 `clientId`、最近一次的位置 `move`，以及泡泡的 `after` cursor。
- **回應：** 團的 `revision`、在線玩家、新泡泡。
- **revision 變大時：** `useRoom` 重抓快照，比本機舊的快照會被丟棄。
- **斷線恢復時：** 先用原本的 `requestId` 重送還沒確認的點餐，再重抓快照，所以不會漏單，也不會重複下單。
- **授權：** 每次請求都以 `requireMember` 驗證成員資格，非成員回 401；位置只能寫成自己的 `member_id`。

店家後台每秒輪詢一次 `POST /api/stores/:id/live`，並以 `requireOwner` 驗證。

### 伺服器成本

worker 在每個 isolate 快取一份已開啟的快照，以 revision 為鍵。每次輪詢只送一個查詢，D1 的 revision 沒變就不回傳 blob，也不重新解碼 SQLite。寫入路徑一律自己開新的一份，不使用快取。快取上的讀取都必須在第一個 `await` 之前完成，見 `worker/index.ts` 的 `liveSnapshot`。過期 presence 的清理只在約 5% 的輪詢上執行；讀取時本來就會依 `seen_at` 過濾。

## 輪詢間隔

定義在 `web/adapters/poll-policy.ts`：

| 狀態 | 間隔 | 條件 |
| --- | --- | --- |
| 活動中 | 250ms | 5 秒內自己移動過，或觀察到 revision、在線玩家、泡泡有變化 |
| 閒置 | 1s | 前景頁面，5 秒內沒有變化 |
| 背景分頁 | 5s | `document.visibilityState === "hidden"`；仍在 presence 的 10 秒 TTL 內，所以仍顯示在線 |
| 斷線 | 1.5s | 上一次請求失敗 |

慢速輪詢時，只要自己開始移動或切回分頁，就會立刻同步一次。

## 延遲目標與實測

實測方式：本機 `wrangler dev` 建置 Sites 版，用兩個獨立的 Chrome context 跑同一團。每一項只量一次，日期為 2026-11-07。

| 項目 | 目標 | 實測 |
| --- | --- | --- |
| 他人的點餐出現在前景頁面（閒置時） | ≤ 1.5s | 0.86s |
| 他人的點餐出現在前景頁面（活動中） | ≤ 0.5s | 0.22s |
| 角色移動（房間活動中） | ≤ 0.5s，即輪詢 250ms 加上送出間隔 100ms | 未單獨量測 |
| 閒置後他人第一次移動 | ≤ 1.5s | 未單獨量測 |
| 新成員加入後出現在在線人數 | ≤ 1.5s | 0.46s |
| 斷線恢復後補上漏掉的訂單 | ≤ 3s | 1.78s |
| 收單同步到團員畫面 | ≤ 1.5s | 0.18s |

### 請求量

| 狀態 | 改版前 | 改版後 |
| --- | --- | --- |
| 前景閒置 | 約 3.7 次/秒 | 1 次/秒 |
| 活動中 | 約 3.5 次/秒 | 4 次/秒 |
| 背景分頁 | 約 3.7 次/秒 | 0.2 次/秒 |

估算範例：30 人、20 分鐘，假設 25% 時間活動中、50% 前景閒置、25% 背景，每人平均約 1.55 次/秒，一場約 5.6 萬次 `/live` 請求；改版前固定每 250ms 一次，約 14.4 萬次。依 #2 引用的 2027 擬議費率（每 10 萬次請求約 16 credits），一場約 9 credits，改版前約 23 credits。託管費用在 2026-12-31 前免費，實際額度依帳號方案而定。

## 截止時間與自動收單（#15）

團主可在開團時或開團後設定截止時間（`rooms.deadline_at`，一分鐘到 24 小時內）。Sites 上的 Cron 尚未驗證，因此不依賴排程，改由三個觸發點收單：

| 觸發 | 環境 | 說明 |
| --- | --- | --- |
| 團員頁面倒數歸零 | 兩者 | 前端呼叫 `POST /api/rooms/:id/expire`，失敗每 3 秒重試；伺服器時間未到則不做事 |
| 任何寫入請求 | Sites | `worker/index.ts` 在 dispatch 前執行 `closeExpiredRooms`，與該次寫入一起提交 |
| 每 5 秒掃描 | Node | `server/index.ts` 的計時器 |

- 點餐、加入與修改截止一律以伺服器時間判斷，收單稍有延遲也不會接受逾時點餐。
- 手動與自動收單共用 `closeInTx`，在同一寫入交易內檢查 `status`，重試或並發都不會重複建立店家訂單。
- 延遲目標：只要有團員開著頁面，收單會在截止後約 1 至 3 秒完成（實測取決於輪詢與重試）。**沒有任何人開著頁面、Sites 上也沒有其他寫入時，不會準時收單**；但逾時點餐仍會被拒，下一次有人開頁面或任何寫入時就會補收。
- 截止前 5 分鐘只在頁面內提醒；離開頁面的推播通知由 #19 處理。

## 已知限制

- 店家頻道回傳的是全站 revision，任何一團有寫入，店家頁都會重抓一次訂單，最多每秒一次。
- 身分目前是 `lt_sid` session。綁定 ChatGPT 帳號與內部成員資格由 #38 處理。
- 只在本機 wrangler 驗證過，Sites 雲端上的多人實測尚未進行。
- `scripts/smoke.mjs` 寫死的走路路線在 Sites 的種子資料下會被建築擋住，`main` 也一樣，與本次同步改動無關。
